# B-001 - Double-clicking the release `.exe` shows an argparse usage error instead of the installer

- **Bug found:** 2026-09-20 00:33
  - Current app version: 0.1.0
- **Assessed severity:** High
- **Current state:** Fixed
- **Bug fixed:** 2026-09-20 01:02 (first attempt 00:52 did not work — see below)
  - Fixed during version: 0.1.0 (unreleased at time of fix)

  ## Summary of bug

  Double-clicking the `.exe` downloaded from the GitHub release prints

  ```
  usage: wrsrcli [-h] [--version] <command> ...
  wrsrcli: error: the following arguments are required: <command>
  ```

  and nothing else. This is exactly the failure `cli.main`'s first-run branch
  was added to prevent (see D-014), so the branch was not firing.

  The branch is guarded by `install.launched_from_explorer()`, which called
  `GetConsoleProcessList` and concluded "double-clicked" only when the count
  was exactly 1 — the reasoning being that Explorer gives a console
  application a console of its own, whereas a terminal shares its own.

  ### Root cause

  **PyInstaller's `--onefile` build is two processes.** The bootloader
  unpacks the payload to a temp folder and launches a *second* copy of the
  same executable, which is where the Python code actually runs. Measured on
  the reporter's machine with a frozen probe:

  ```
  process chain:  probe.exe (child, runs our code)
                  probe.exe (bootloader)
                  explorer.exe
                  svchost.exe ...
  console_process_count: 2
  ```

  So in the shipped build the count is **never** 1 — the bootloader is
  attached to the same console — and the immediate parent is **never**
  Explorer, because our own bootloader sits in between. The original test
  could not have worked in any `--onefile` release, on any console host.

  D-014's commit message records measuring "1 versus 3 on this machine",
  which is consistent: that measurement was taken on an unfrozen run, where
  there is no bootloader generation and the heuristic does hold. The release
  build was never exercised the same way.

  ### Consequences for users

  This is the first thing anyone who downloads the tool will do, and it
  failed for every user of every release build. The user is shown an argparse
  error with no indication of what to do next, and never sees the offer to
  install. The installer was effectively unreachable for anyone who did not
  already know to run the binary from a terminal.

  It is cosmetic rather than destructive — no data is at risk, and the tool
  works normally when invoked with arguments — but it blocked the intended
  first-run experience entirely.

  ## First fix attempt (00:52) — insufficient, wrong diagnosis

  The first fix replaced the process-count test with a check on the
  **immediate parent process**, on the theory that the count was being thrown
  off by Windows Terminal being the default terminal application on Windows
  11 — a Terminal-hosted console having more than one process attached.

  That theory was wrong, and the fix did not work: the reporter rebuilt from
  the release workflow and saw the identical error. The theory was plausible
  and was never tested against a frozen binary, only against the decision
  logic in isolation and against an unfrozen process. Testing the actual
  artifact would have shown the bootloader immediately. The console host is
  irrelevant to this bug.

  ## Summary of fix

  `launched_from_explorer()` now asks who started us **past our own
  bootloader**. `ancestor_names()` walks the process tree from this process
  upward and returns the chain; `launching_process_name()` skips every
  leading generation whose image name matches our own executable's, and
  returns the first one that differs. A result of `explorer.exe` means a
  double-click.

  Skipping by name is what makes this work for `--onefile` without depending
  on PyInstaller internals or on how many bootloader generations there
  happen to be. Explorer appearing *further* up the tree is deliberately not
  enough — every shell is itself ultimately a child of Explorer — so only the
  first non-self ancestor is consulted.

  The original test survives as `console_is_ours_alone()`, used as a fallback
  when the chain cannot be read at all. It cannot fire in the shipped build,
  and its docstring now says so rather than implying it is a working signal.
  Exceptions during detection are swallowed: the worst case of guessing wrong
  is the ordinary usage message, and a crash on startup would be worse than
  the bug.

  **Verified end to end, on the real artifact this time.** A `--onefile`
  binary was built with PyInstaller 6.22.3 and launched through
  `explorer.exe`, which is what a double-click does:

  - Launched via Explorer: `launching_process_name()` returned
    `explorer.exe` and `launched_from_explorer()` returned True, with the
    bootloader visible in the chain and the console count at 2 — the exact
    conditions that defeated both earlier signals.
  - The real `wrsrcli-windows-amd64.exe`, double-clicked through Explorer,
    stayed alive sitting at the install prompt instead of exiting with the
    usage error.
  - The same binary run from a shell with no arguments still prints the
    usage error and exits 2, and `--help` is unaffected.
  - Launched from `powershell.exe`: launcher resolved to `powershell.exe`,
    detection False.

  Plus 17 checks over the decision logic, including the onefile chain,
  multiple bootloader generations, five different shells, a shell that was
  itself started from Explorer (must be False), both fallback paths, and a
  raising walk not crashing startup.
