# B-001 - Double-clicking the release `.exe` shows an argparse usage error instead of the installer

- **Bug found:** 2026-09-20 00:33
  - Current app version: 0.1.0
- **Assessed severity:** High
- **Current state:** Fixed
- **Bug fixed:** 2026-09-20 00:52
  - Fixed during version: 0.1.0 (unreleased at time of fix)

  ## Summary of bug

  Double-clicking the `.exe` downloaded from the GitHub release prints

  ```
  usage: wrsrcli [-h] [--version] <command> ...
  wrsrcli: error: the following arguments are required: <command>
  ```

  and the window stays open showing only that. This is exactly the failure
  `cli.main`'s first-run branch was added to prevent (see D-014 and the
  commit that introduced `first_run`), so the branch is not firing.

  The branch is guarded by `install.launched_from_explorer()`, which calls
  `GetConsoleProcessList` and concludes "double-clicked" only when the count
  is exactly 1 — the reasoning being that Explorer gives a console
  application a console of its own, whereas a terminal shares its own.

  That reasoning holds for the legacy `conhost.exe` host it was measured
  against. It does not hold on Windows 11 when **Windows Terminal is the
  default terminal application**, which is the default on current Windows 11
  and is what the reporter is running: the console is hosted by Windows
  Terminal via `OpenConsole.exe`, more than one process is attached, the
  count is greater than 1, and the double-click goes unrecognised. The
  screenshot shows the error inside a Windows Terminal tab titled with the
  Downloads folder, which is the signature of exactly this path.

  ### Consequences for users

  This is the first thing anyone who downloads the tool will do, and it
  fails on a default Windows 11 configuration. The user is shown an
  argparse error with no indication of what to do next, and never sees the
  offer to install. The installer is effectively unreachable for anyone who
  does not already know to run the binary from a terminal.

  It is cosmetic rather than destructive — no data is at risk, and the tool
  works normally when invoked with arguments — but it blocks the intended
  first-run experience entirely.

  ## Summary of fix

  `launched_from_explorer()` now asks **who started this process** instead of
  inferring it from how many processes share the console. A new
  `parent_process_name()` walks a `CreateToolhelp32Snapshot` process list
  once and returns the parent's image name; a parent of `explorer.exe` means
  a double-click. That signal is independent of which console host Windows
  chose, so Windows Terminal and legacy `conhost` behave identically.

  The old attached-process test is kept, renamed `console_is_ours_alone()`,
  and consulted as a fallback when the parent cannot be determined — a
  parent that has already exited, or a snapshot that fails. Either signal is
  sufficient; neither fires when the tool is run from a shell, so terminal
  users are never interrupted by the install prompt. Any exception during
  detection is swallowed, because the worst case of getting this wrong is
  the ordinary usage message, and a crash on startup would be worse than
  the bug being fixed.

  Explorer is also the parent for the Run dialog, the Start menu and the
  context menu's "Open". All of those equally mean "no terminal is waiting",
  so treating them as a double-click is correct rather than incidental.

  **Verified:** 13 checks over the decision logic — the Windows Terminal
  case that caused this bug, the legacy conhost case that already worked,
  launches from `powershell.exe`/`cmd.exe`/`pwsh.exe`/`bash.exe` (none of
  which may trigger the prompt), an unknown parent falling back both ways,
  and a raising detector not crashing startup. `parent_process_name()` was
  separately cross-checked against `Win32_Process`'s `ParentProcessId` and
  agreed. Running with no arguments from a terminal still produces the
  usage error and exit code 2, unchanged.

  **Not verified here:** the end-to-end double-click of a PyInstaller build
  on a stock Windows 11 desktop. That needs a release binary and a real
  Explorer launch, so it is outstanding until the next build is downloaded
  and double-clicked — the same criterion as the original report.
