# D-012 - `manual-check` compares against the mtime the import left, not the backup's timestamp

- **Decided:** 2026-09-19 23:57

## Issue

`SPEC.md` §4.7 specifies the game-file branch of the staleness check as:

> compare the actual filesystem modified timestamp of the file at that
> game path against the backup entry's recorded timestamp. If the file's
> mtime is newer → flag.

Implemented literally, this flags a file **immediately after a clean
import**, with nothing reverted. Phase 9's verification caught it on the
first run: `manual-check` reported the just-imported file as possibly
reverted.

The cause is `shutil.copy2`, which preserves the *source* file's
modification time. After an import the placed file's mtime is the workshop
source's mtime, not the moment of the copy. Whenever that source is newer
than the instant the backup was taken — which is any workshop item
downloaded or updated recently — the comparison trips.

§4.7 does accept that this check "can false-positive". That allowance was
clearly meant for outside interference touching a file's mtime, not for
the command flagging every import the moment it completes, which would
make `manual-check` useless as a signal.

Tradeoffs considered:

1. **Record the destination's mtime just after the import writes it, and
   compare against that.** Directly measures the thing the check cares
   about: has anything changed this file since *we* placed it. One extra
   number per backup entry.
2. **Stop preserving source mtimes (use `copy` rather than `copy2`).**
   Would make mtime mean "when the import ran". Rejected: it discards
   metadata that legitimately belongs to the copied file, to work around a
   comparison problem.
3. **Compare against the run's completion time.** Simpler, but wrong for
   the same reason as the backup timestamp — the placed file's mtime is
   the source's, which can sit either side of it.

## Decision

A `copy` backup entry gains a `placed_mtime` field, recorded from the
destination immediately after the file is written. `manual-check` compares
the file's current mtime against `placed_mtime` and flags it only if it is
strictly newer.

Entries without the field — written before this change — fall back to
§4.7's original comparison against the entry timestamp, so an existing
backup manifest keeps working.

The `.acf` branch for `[WORKSHOP]/` destinations is unchanged; comparing
the item's `timeupdated` against the backup timestamp is correct there,
because that value reflects when Steam updated the item rather than
anything wrsrcli wrote.

**Known limitation, unchanged:** only backed-up files are tracked, per
§4.7's "every tracked backup entry". An import that *adds* files without
overwriting anything produces no backup entries, so those files are not
checked for reversion. Flagged here rather than silently widened.

`SPEC.md` §4.7 updated.
