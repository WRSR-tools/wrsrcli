# D-013 - Release build: tag-triggered, Windows-only, single raw `.exe`

- **Decided:** 2026-09-19 23:57

## Issue

Three things had to be settled to write the release workflow.

**1. The trigger** — open item #6, which `SPEC.md` §6 marks OPEN
(push / tag / manual dispatch).

**2. Target platforms.** The project's binary-release guidance describes a
five-platform matrix (Linux amd64/arm64, macOS amd64/arm64, Windows
amd64). That conflicts with this project's scope: `SPEC.md` §1 is "Windows
only for v1" and `AGENTS.md` says not to add cross-platform abstractions
that are not needed yet. More concretely, `steam.py` imports `winreg` at
module level to read `HKCU\Software\Valve\Steam`, so a Linux or macOS
build would fail to import, and there is no Steam-path source on those
platforms to fall back to.

**3. The PyInstaller entry point.** `[project.scripts]` covers
`pip install`, but PyInstaller needs a real script to freeze.
`wrsrcli/__main__.py` cannot serve: frozen as a top-level script, its
`from .cli import main` relative import has no package context.

## Decision

**Trigger:** `push` on tags matching `v*`, plus `workflow_dispatch`. A
version tag cuts a GitHub Release with the `.exe` attached; manual
dispatch builds and uploads an artifact without creating a release, so the
workflow can be exercised without a throwaway tag. Open item #6 is closed.

**Platforms:** `windows-latest` only, producing
`wrsrcli-windows-amd64.exe`. The naming convention `{repo}-{arch}[.exe]`
and the "raw executable, never an archive" rule are kept, so adding
platforms later is a matrix addition rather than a rewrite. The remaining
release conventions are followed: actions pinned to Node 24-native
versions, PyInstaller deliberately unpinned so prebuilt bootloaders are
used, and `python-version: "3.x"` rather than a pinned minor.

**Entry point:** a three-line `entrypoint.py` at the repo root, used only
by PyInstaller. `wrsrcli/__main__.py` is untouched and remains the entry
for `python -m wrsrcli`.

**Verification status.** Built locally with PyInstaller 6.22.3 and
confirmed working: `--version`, `--help` listing all 10 subcommands,
`path --auto-detect` exercising the bundled `winreg`, and a full `import`
run exercising the bundled PyYAML, all from a frozen binary run outside
the repo with `PYTHONPATH`/`PYTHONHOME` cleared.

What is **not** verified is Phase 10's literal criterion — running on a
Windows machine with no Python installed. This machine has Python, and
that claim cannot honestly be made from here. `--onefile` embeds the
interpreter, and the clean-environment run is supporting evidence, but
confirming it needs a machine without Python. The workflow's own smoke
test step runs `--version` and `--help` on the runner, which also has
Python.
