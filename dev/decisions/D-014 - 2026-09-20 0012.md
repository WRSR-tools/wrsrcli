# D-014 - `wrsrcli install` puts the standalone executable on the user's PATH

- **Decided:** 2026-09-20 00:12

## Issue

Phase 10 produces a single `wrsrcli-windows-amd64.exe`, but nothing puts it
anywhere useful. A user downloads it from the release and it sits in
Downloads, so every invocation needs a full path. Reported directly by the
project owner after installing the release build.

The same friction appeared with the pip install during development: pip
placed `wrsrcli.exe` in
`...\pythoncore-3.14-64\Scripts`, which is not on this machine's PATH, and
pip warned about exactly that at install time.

Worth stating plainly, because it shaped the fix: **packaging metadata
cannot solve this.** `[project.scripts]` entry points are placed in the
environment's own Scripts directory by design; a package is not permitted
to install outside its prefix, and no `pyproject.toml` setting relocates
them. The fix has to be an action the user takes, not a build-time setting.

Tradeoffs considered:

1. **A self-install subcommand.** The binary copies itself to a per-user
   programs folder and adds that folder to the user's PATH. This is the
   established pattern for single-binary CLIs, needs no admin rights, and
   works for the standalone `.exe`, which is the actual distribution.
2. **A separate installer script in the release.** Keeps PATH logic out of
   the tool, but adds a second artifact to download and run, and a `.ps1`
   from the internet is a worse prompt than a command in a tool the user
   already chose to run.
3. **Document "put it on your PATH yourself".** Zero code. Rejected: it is
   the status quo, and it is the thing that was reported as a problem.
4. **Write into Python Manager's shim folder** (`...\Local\Python\bin`,
   which *is* on PATH here). Rejected: that directory belongs to another
   tool, is specific to this machine's Python setup, and has nothing to do
   with the standalone build.

## Decision

A new `wrsrcli install` subcommand:

- Copies the running executable to `%LOCALAPPDATA%\Programs\wrsrcli\wrsrcli.exe`,
  or to `-p/--path` if given (matching `steamcmd`'s flag convention, D-008).
- Adds that folder to the **user** PATH (`HKCU\Environment`) if not already
  present, then broadcasts `WM_SETTINGCHANGE` so new shells pick it up.
  The machine-wide PATH is never touched and no admin rights are needed.
- Is idempotent: reinstalling reports the folder was already on PATH, and
  never appends a duplicate entry.
- **Refuses when not running frozen**, explaining that a pip install
  already placed a script in that environment's Scripts folder. Copying an
  interpreter around would not produce a working command.

**Note this is an addition to `SPEC.md` §4's command list**, which
`AGENTS.md` says should match the spec. Added at the project owner's
explicit request; §4 updated to match rather than left to drift.

**PATH safety.** Editing PATH can break a user's shell, so the string
handling is a pure function (`extend_path`) tested independently of the
registry, and the registry value's type is read and preserved rather than
assumed. That last point is not theoretical: this machine's user PATH
begins with the unexpanded `%USERPROFILE%\AppData\Local\Microsoft\WindowsApps`,
which rewriting as `REG_SZ` instead of `REG_EXPAND_SZ` would have broken.
A PATH value that is not text is refused rather than overwritten. Windows
caps an environment variable at 32767 characters, so an append that would
cross that limit is refused rather than written — exceeding it truncates
PATH and breaks the user's shell, which is far worse than not installing.

**Not included:** an uninstall path. Anything that edits PATH should be
reversible, and removing the entry is left undone for now rather than
silently assumed unnecessary. Flagged here as the obvious follow-up.
