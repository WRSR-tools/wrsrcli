# D-015 - `wrsrcli uninstall` reverses `install`, and is recorded after the fact

- **Decided:** 2026-09-20 00:40

## Issue

D-014 added `wrsrcli install`, which copies the standalone executable to
`%LOCALAPPDATA%\Programs\wrsrcli` and appends that folder to the user PATH.
It closed with:

> **Not included:** an uninstall path. Anything that edits PATH should be
> reversible, and removing the entry is left undone for now rather than
> silently assumed unnecessary. Flagged here as the obvious follow-up.

`uninstall` was then implemented in the very next commit, along with the
double-click first-run flow, without a decision record. So the code and the
records disagreed: D-014 said no uninstall existed and was not superseded,
`SPEC.md` §3 documented `install` but not `uninstall`, and `AGENTS.md`'s
command list named ten subcommands where the CLI has twelve.

This record is therefore written **after** the code it describes, which
`AGENTS.md` asks not to happen. Recording that plainly is the point: the
alternative — quietly writing the record as though it had come first, or
quietly deleting the feature — would hide a real process failure. The
drift was found during a repository review, not by the work that caused it.

## Decision

`uninstall` stays, and is specified in `SPEC.md` §3 alongside `install`.
D-014's "Not included" paragraph is superseded by this record.

Scope and mechanics, as implemented:

- Removes `wrsrcli.exe` from the install directory, and removes that
  directory from the user PATH under `HKCU\Environment`.
- `-p`/`--path` mirrors `install`'s, for a non-default location.
- A running executable cannot delete itself on Windows. Rather than
  resorting to a self-deleting batch stub or a scheduled delete — both of
  which are the shape of things malware does, and neither of which is worth
  it here — the binary is left in place and the user is told. The PATH
  entry is removed regardless, so the visible effect is achieved.
- PATH removal preserves every other entry byte-for-byte, including blanks
  and unexpanded `%VAR%` segments. The same reasoning as D-014 applies: a
  wrong write here breaks the user's shell, so the string handling is a
  pure function (`shrink_path`) that never rewrites what it was not asked
  to remove.
- The install directory is `rmdir`'d only when empty, so a user who
  installed into a folder holding other things keeps them.

**`%APPDATA%\wrsrcli\` is deliberately out of scope.** Config, the manifest
and the backup store all survive. The backup store is the only copy of
files that imports overwrote, and destroying it because someone tidied up a
CLI binary would be exactly the kind of irreversible loss this tool exists
to prevent. Uninstalling the program is not the same intent as discarding
the data, and conflating the two is a one-way mistake.

### Tradeoff accepted

Leaving `%APPDATA%\wrsrcli\` behind means `uninstall` is not a complete
removal, and a user who wants no trace has to delete that folder by hand.
That is documented in `dev/docs/Install.md`. The asymmetry is intentional:
leaving data behind costs the user a manual delete, whereas removing it
costs them their only backups.

## Superseded

Not superseded.
