# D-016 - First-run screen wording, and how colour is handled on the console

- **Decided:** 2026-09-20 01:14

## Issue

B-001 made the first-run installer screen reachable again. Its wording was
then replaced wholesale, and the new text asks for the title line and the
`Press ENTER to install...` prompt to be set in a rusty red matching the
game's own styling.

Three questions came out of that:

1. How is colour produced at all, given `AGENTS.md` says stdlib first and
   the obvious answer (`colorama`) is a third-party dependency?
2. Which rusty red, and what happens on a console that cannot render it?
3. The new text says "Press ENTER to install", where the old screen asked
   `Install now? [Y/n]:`. What does a non-empty reply mean now?

## Decision

### Colour without a dependency

ANSI escape sequences, written directly. `colorama` exists to paper over
consoles that do not understand them, and this tool already talks to the
Win32 API through `ctypes` in two other places, so the stdlib answer is
neither hard nor unusual here: enable `ENABLE_VIRTUAL_TERMINAL_PROCESSING`
on the stdout handle via `SetConsoleMode` and write the escapes.

The important part is the failure mode. A console that does not understand
escapes prints the raw `←[38;2;183;65;14m` rather than ignoring it, which is
considerably worse than plain text. So `enable_ansi()` returns True only
once VT processing has been confirmed already on or successfully switched
on, and `rust()` is a no-op otherwise. Colour is additionally suppressed
when `NO_COLOR` is set — the widely-honoured convention — and when stdout
is not a terminal, so redirecting to a file gives clean text.

### The shade

`#b7410e`, written as a 24-bit escape. Windows Terminal reproduces it
exactly; legacy `conhost` maps it to the nearest palette entry.

The obvious alternative was `#7a1f1f`, the accent `output-table`'s HTML
already uses. It was rejected for the console: that HTML renders on a light
background (`--bg: #f6f6f4`) where a dark oxide red reads well, whereas a
terminal is conventionally near-black, and `#7a1f1f` on `#0C0C0C` is dim to
the point of being hard to read. `#b7410e` is the same rusted-iron family
carried to a dark background. The two are deliberately not identical,
because they are not shown against the same thing.

### Only ENTER proceeds

A non-empty reply cancels; nothing is installed. This matches D-008's rule
for `steamcmd --install`, so both of the tool's "this will change something
on your machine" prompts behave identically, and neither can be triggered by
a stray keypress followed by ENTER.

It is also a change from the old screen's `[Y/n]`, where `y`, `yes` and
ENTER all proceeded. Nobody can now type `y` and have it install — `y`
cancels. That is the cost of consistency with D-008, and it is accepted
because the failure is safe in the direction that matters: a mistyped reply
installs nothing and the screen explains what to do instead.

### Tradeoff accepted: the screen no longer explains what it will change

The previous wording named the install directory and said that the user PATH
would be extended, that nothing else would change, and that no administrator
rights were needed — all *before* asking. D-014 treated that as part of
making a PATH edit acceptable. The new text does not say any of it.

This is the requested wording and it stands, but the loss is real and worth
recording rather than absorbing silently. Two things blunt it: the install
directory and the PATH change are both reported immediately afterwards, so
the user still learns exactly what happened, and the screen now carries a
documentation link (`https://wrsr-tools.github.io`) that the old one did
not. If the omission ever causes a complaint, restoring one line naming the
directory would answer it without disturbing the rest of the layout.

Note that link is currently unpublished; the screen points at a site that
has to exist before the next release is handed to anyone.
