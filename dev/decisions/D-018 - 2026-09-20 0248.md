# D-018 - The help screen carries the rust accent, not argparse's palette

- **Decided:** 2026-09-20 02:48

## Issue

The `--help` screen was reported as "quite colorful" in PowerShell, and
asked to read rusty red and industrial instead.

No code in this repo colours the help. The cause is upstream: `argparse`
gained colourised help in **Python 3.14**, switched on by default
(`ArgumentParser(color=True)`), and `.github/workflows/release.yml` asks
for `python-version: "3.x"`. A release built today therefore embeds 3.14
and ships five colours nobody chose — bold blue for `usage:` and the
section headings, bold magenta for the program name, bold green for the
command names, green and cyan for the options.

Three questions followed.

1. How is colour applied without breaking the layout?
2. What happens to argparse's own colour, given the project supports
   Python 3.12 through 3.14?
3. How much of the screen should be coloured?

## Decision

### 1. Colour is applied after layout, never before

`argparse` positions the help column by measuring the command names with
`len()`, which counts escape sequences that occupy no width on screen.
Colouring a name before that measurement inflates it past the column, and
every description is pushed onto a line of its own.

So `_RustHelpFormatter._format_action` calls `super()` first and paints the
invocation in the already-padded result. The check that this holds is exact
rather than visual: stripping every escape from the coloured help must
reproduce the uncoloured help byte for byte. It does, on all three versions.

This is a real constraint, not a theoretical one — 3.14 hit it too, and
solved it with an internal `_decolor` hook that 3.12 and 3.13 do not have.

### 2. argparse's own colour is turned off, not layered under ours

`_RustHelpFormatter._set_color` forces it off. 3.14 applies colour through
that hook (`ArgumentParser._get_formatter` calls `formatter._set_color`),
so overriding it is enough; on 3.12 and 3.13 the hook does not exist and is
never called, so no version check is needed.

The alternative, `ArgumentParser(color=False)`, was rejected: the keyword
does not exist before 3.14, so it would need a version guard at the call
site and would not travel to the subparsers.

**Recorded cost:** `HelpFormatter`'s hooks are underscore-prefixed and carry
no backwards-compatibility guarantee. This is the accepted price of
reusing argparse's layout engine. If it breaks on a future Python, the
escape hatch is to stop asking argparse to lay the screen out at all and
print it directly — the help text is a fixed list of thirteen commands.

### 3. The accent marks structure; descriptions are left alone

Rust on the section headings, the command names, the option strings and the
`usage:` prefix. Every description keeps the terminal's own foreground.

Painting the whole screen was rejected for the reason D-017 gave when it
stopped forcing white on the first-run prompt: the user picked their
foreground colour, and twenty-six lines of one hue is a highlighter, not an
industrial finish. The accent is worth more where it marks fewer things.

Subparsers inherit this through `type(self)` — `add_subparsers` builds each
subcommand from the class of the parser it is called on, so making the
top-level parser a `_RustParser` gives `wrsrcli {command} --help` the same
treatment without thirteen repetitions.

### Open, and deliberately not decided here: the shade fails AA

D-016 chose `#b7410e` for the console by reasoning about dimness, but did
not compute a contrast ratio — where D-017, for the HTML table, did. Doing
that arithmetic now:

| | on `#0c0c0c` (Windows Terminal) | on `#012456` (legacy PowerShell) |
|---|---|---|
| `#b7410e` (D-016) | 3.52:1 | 2.72:1 |
| `#d9793f` (D-017 dark) | 6.29:1 | 4.87:1 |

`#b7410e` clears WCAG AA (4.5:1) against neither background. `#d9793f` —
already in the codebase as the table's dark-mode rust — clears both.

This matters more here than on the first-run screen. There the accent sits
on a title and one word of a prompt, both of which repeat in plain text
nearby. Here the coloured text *is* the information: the command names are
the least legible thing on a screen whose entire job is listing them.

`#b7410e` is kept for now regardless, because changing it means changing
D-016's recorded choice and the first-run screen with it, and that is not
this change's call to make. Flagged for a decision of its own.
