# D-020 - Dependency tracking in `scan`, and links in the table

- **Decided:** 2026-09-20 21:45

## Issue

Steam records an item's "required items", and nothing in `wrsrcli` has ever
surfaced them. A scan of the author's own library found four installed mods
requiring `3773169177` (TesmioLoader) which is not installed and not even
subscribed — a state that had been quietly breaking those mods with no
local signal of any kind.

Tracking them raises four questions.

1. `scan` is specified in SPEC 4.1 as a purely local operation, over the
   `.acf` and the workshop folder. Dependencies exist only in the Steam Web
   API, and only behind a key. Putting them in `scan` makes it reach the
   network.
2. The manifest would gain a field whose truth can change without the
   manifest being rewritten: whether a dependency is installed.
3. WMLS v1 already has `depends-mandatory:`/`depends-optional:` (D-018).
   Two dependency concepts now exist in one tool.
4. SPEC 4.2 requires the rendered table to work standalone with no network
   access, and the request is to add links to Steam.

## Decision

### 1. `scan` fetches dependencies when a key is set, and never fails for it

Dependencies are only obtainable from `IPublishedFileService/GetDetails`
with `includechildren=true`, which requires a key. The keyless
`GetPublishedFileDetails` this tool already used returns no dependency
field at all, and `GetCollectionDetails` answers only for real collections
(`result: 9` for an ordinary item).

So `scan` is no longer strictly local. The alternative — resolving
dependencies in `output-table` instead, leaving `scan` untouched — was
rejected because the manifest is the tool's record of what is installed,
`manual-check` and the import machinery read it, and a dependency is a
fact about an installed item rather than a fact about a rendering of it.

The local inventory remains the job `scan` cannot fail at. Dependency
enrichment runs after the `.acf` and `workshopconfig.ini` pass has already
produced its entries, and any API failure is reported as a warning and
leaves the manifest otherwise complete, exactly as D-007 does for the
table. With no key stored, `scan` says so once and writes the same
manifest it always did. A manifest written without a key is not wrong, it
is unenriched, and `output-table` distinguishes the two by the absence of
the key rather than by the absence of the field.

This does not breach the AGENTS.md rule that network actions be opted into
explicitly. That rule governs *downloads and subprocess execution* —
SteamCMD fetching files. `scan` already had a sibling in `output-table`,
which has queried the Web API for metadata since Phase 5 with no prompt.
Reading metadata about items the user already has is not the category the
rule is protecting.

### 2. The manifest stores what Steam said, not what the disk says

Each entry gains `dependencies`: a list of `{item_id, name, creator_id,
creator}`. What is deliberately *not* stored is whether each dependency is
installed.

That flag would be a second copy of something the manifest already knows —
the set of installed items is the manifest's own entry list — and it would
be the copy that goes stale first: install the missing dependency, and
every other entry's flag silently becomes a lie until the next scan.
Deriving it at render time from the entries in the same file makes the two
incapable of disagreeing.

`name`, `creator_id` and `creator` *are* stored, because a dependency that
is not installed has no local folder, no `workshopconfig.ini` and no owner
id anywhere on disk. Only the API knows them, so not storing them would
mean `output-table` could not name an unmet dependency without repeating
the whole lookup.

### 3. Steam's dependencies and WMLS's are different things, and stay apart

Steam's required-items list is author-declared, carries no message, and
has no notion of optionality. WMLS v1's `depends-optional:` exists
precisely to carry "this is nice to have, and here is why" — information
Steam does not model. So the two are not merged, and nothing here reads
or writes an import list.

The consequence is that Steam's list can never be generated from a WMLS
file or vice versa. It can, later, be used to *check* one: warning when a
list's `depends-mandatory:` omits something Steam calls required. That is
left unbuilt rather than guessed at.

### 4. Hyperlinks are navigation, not external references

SPEC 4.2's standalone requirement is about what the file *loads* — no CDN,
no external stylesheet, no remote script, so the table renders identically
forever on a machine with no network. An `<a href>` loads nothing; it is
inert until the reader clicks it, and a click is the reader choosing to
leave. The rendered file still has zero external references in the sense
4.2 means, and that property is re-checked rather than assumed.

Links open in a new tab with `rel="noopener noreferrer"`, so the workshop
page cannot reach back into the table's window.

### 5. The fold is per row, and only exists where there is something in it

Dependencies render as a fold-down under the item's own row, headed
`DEPENDENCY` for one and `DEPENDENCIES` for more than one, listing
`- {steamid} {name} ({creator}) (OK|Not installed)`.

A column of counts was rejected: the useful question is not "how many"
but "which ones, and are they here", and that is a list. Rows with no
dependencies get no toggle at all rather than a disabled one, so the
control's presence is itself the signal.

The fold is collapsed by default. A library where most items declare a
dependency — 16 of 21 here — would otherwise render mostly as dependency
lists, burying the table the section is about.

The fold column appears whenever any row has dependencies, in *both*
modes — not only when a key is set. This corrects a first cut that tied it
to API mode by analogy with author/posted/size. Those three are omitted in
no-API mode because 4.2 gives them no local source; dependencies, once a
scan has stored them, are in the manifest, which makes them exactly as
local as `item_type`. Tying the fold to the key would have hidden data the
tool already had, purely because it was read from a file rather than
fetched again.

## Superseded

Not superseded.
