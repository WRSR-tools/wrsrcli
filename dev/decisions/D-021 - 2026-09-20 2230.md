# D-021 - `wrsrcli update`, and status accordions in the table

- **Decided:** 2026-09-20 22:30

## Issue

D-020 surfaced unmet dependencies but offered no way to act on them, and
said nothing about items whose installed version is behind the workshop's.
Adding both raises questions the request does not settle.

1. `import` downloads through SteamCMD into SteamCMD's *own* content
   folder, not Steam's. An `update` that did the same would leave the game
   unable to load what it fetched, and the next `scan` — which reads
   Steam's `.acf` — would still report the dependency missing. The feature
   would appear to work and change nothing.
2. `scan` treats the `.acf` as the definition of "installed". Anything
   `update` places on disk is invisible to it.
3. Staleness needs the installed version's timestamp. The `.acf` has one;
   an item `update` downloaded has no `.acf` entry at all.
4. `build_rows` currently prefers the API's `time_updated` over the
   `.acf`'s for the Updated column.
5. AGENTS.md requires downloads to be explicitly opted into, and forbids
   overwriting anything outside the backup mechanism.

## Decision

### 1. `update` downloads into Steam's workshop folder

SteamCMD fetches into its own tree, as it always has, and `update` then
moves the result into
`steamapps/workshop/content/784150/{id}/`, where the game looks. The two
rejected alternatives were leaving it in SteamCMD's folder — correct-
looking output, no effect on the game, and a dependency that stays
"missing" forever — and opening workshop pages for the user to subscribe,
which is the tidiest outcome for Steam's own bookkeeping but is not a
command that does anything on its own.

The consequence is accepted rather than hidden: Steam does not know about
these items. They are absent from the `.acf`, Steam will not update them,
and a Steam-side verify may remove them. Subscribing in Steam remains the
better route when the user is willing, and `update` says so on completion.

### 2. Installed means the `.acf` *or* a folder on disk

`scan` keeps the `.acf` as its primary source and then adds any numeric
folder in the workshop directory that the `.acf` does not mention. Without
this, everything `update` does is invisible to the tool that reported the
problem.

A folder-only item is not an error and is not warned about *if* `wrsrcli`
put it there. One it did not — a hand-copied folder, or a leftover — still
gets a warning naming it, because that is a state the user should know
about and the old code silently ignored it.

### 3. `update` records the version it fetched

An item with no `.acf` entry has no installed-version timestamp, so
staleness could never be judged for exactly the items `update` creates.
`update` therefore writes `%APPDATA%\wrsrcli\downloads.json`, mapping item
id to the `time_updated` of the version it fetched and when it did so.
`scan` reads it for folder-only items and leaves `date_updated` null when
even that is unavailable.

This is the tool keeping its own books where Steam keeps none. It is
deliberately not merged into `config.json`, which is user settings, or the
manifest, which is rebuilt wholesale by every scan.

### 4. The Updated column shows the installed version, not the workshop's

Preferring the API's `time_updated` was reasonable when nothing compared
the two: it was simply the better-sourced value. It is wrong now. The
whole point of the Asset status accordion is that local and remote can
differ, and showing the remote timestamp in a column labelled Updated
would display the version the user does *not* have, hiding the very
condition being reported.

Updated is therefore the installed version's time, from the `.acf`, with
the API's value used only to decide whether an update exists. An item is
out of date when the workshop's `time_updated` is strictly greater than
the installed one; equal timestamps and a missing remote value both mean
up to date, so a failed or partial API response never invents work.

### 5. Both accordions, and what they say

Two accordions sit above the table: `Dependencies` and `Asset status`,
each headed with its own state — `(OK)` or `(Dependencies missing)` /
`(Update needed)` — so the state is readable without opening either. A
clean accordion is green and a problem accordion red, using colours that
hold their contrast in both themes rather than raw named colours.

They are collapsed when clean and open when not: a green "no action
needed" panel has nothing inside worth unfolding, while a red one is the
reason the user is looking.

The Asset status accordion needs the API and appears only when the table
was built with a key. The Dependencies accordion reads the manifest, so it
appears whenever dependencies were scanned, key or not (D-020).

The specified line "The following items have needs to be updated" is
rendered "The following items need to be updated" — the meaning is
unambiguous and the original does not parse. Everything else is verbatim.

### 6. Downloads are prompted, and replacements are backed up

`update` prints everything it intends to fetch and waits for ENTER, the
same opt-in `steamcmd --install` uses (D-008). Anything else cancels and
nothing is downloaded.

Replacing an out-of-date item means removing a folder Steam owns, so it
goes through `backup.Run.stash_removal` first, keyed on that item id.
`rollback` can therefore undo an update exactly as it undoes an import,
and the AGENTS.md rule that no overwrite bypasses the backup mechanism
holds. A fresh dependency overwrites nothing and is simply placed.

Each item is its own run, matching D-018's "one item is one generation", so
a failure part-way leaves the items already updated recorded and undoable.

## Superseded

Supersedes D-020's implicit acceptance that the API's `time_updated` is
the right value for the Updated column; see §4 above. The rest of D-020
stands.
