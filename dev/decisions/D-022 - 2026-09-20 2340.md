# D-022 - Staleness from the `.acf`, with the Web API as the upgrade

- **Decided:** 2026-09-20 23:40

## Issue

D-021 made the Asset status accordion API-only, on the assumption that the
workshop's current version had no local source. Inspecting a real
`appworkshop_784150.acf` shows otherwise: every `WorkshopItemDetails` block
carries `latest_timeupdated` and `latest_manifest` beside `timeupdated` and
`manifest` — Steam's own record of the newest version it knows about. All
21 items on this machine have both fields.

So staleness is answerable with no key and no network, and D-021 spends an
API call on a question already answered on disk. That leaves two questions:
which source wins when both exist, and how much the local answer should be
trusted.

## Decision

### 1. The API wins where it answers; the `.acf` answers otherwise

`updates.outdated` takes the API's `time_updated` when `details` carries the
item and falls back to the entry's `date_latest` from the `.acf`. The API
is live; the `.acf` is only as fresh as Steam's own `TimeLastFullCheck`, so
it can lag a publish by however long Steam waits between syncs. Preferring
the fresher source where it exists costs nothing, since a key-holding user
is already making that call for file sizes and dates.

The fallback is per item, not per run. A partial API response — some items
returned, some not — leaves the rest on the `.acf` rather than silently
reporting them as current.

### 2. Neither source means the panel is absent, not green

`can_check_staleness` is true with a key, or when any entry carries
`date_latest`. With neither — an old manifest scanned before this change,
or items only wrsrcli placed — the Asset status accordion does not render
at all. Claiming "All assets are up to date" on the basis of having no way
to check would be the worst of the three possible outputs.

Items `update` placed are exactly this case: Steam has no `.acf` entry for
them, so it knows of no newer version either, and `date_latest` is null.
Only the API can judge those, which is one more reason subscribing beats
sideloading.

### 3. The panel says which check ran

Where the answer came from the `.acf`, the accordion adds, in muted text:
"Checked against Steam's own record, as of its last sync. Set an API key
for a live check."

Steam's cached view is worth acting on — it is how Steam itself decides to
update something — but it is not a live check, and presenting it as one
would be the kind of quiet overclaim the rest of this tool avoids. The
specified success and failure text is unchanged; this is an addition
beneath it.

### 4. `update` follows the same rule

Without a key, `update` now still finds out-of-date items. An API failure
degrades to the `.acf` rather than abandoning the check, and the version
recorded in `downloads.json` comes from whichever source judged the item
stale.

The practical effect is that `wrsrcli update` becomes useful to someone who
never sets a key: dependencies already came from the manifest, and now
staleness comes from the `.acf`. D-021's asymmetry — Dependencies keyless,
Asset status not — is gone.

## Rejected

**Faking `.acf` entries** to make items appear installed or current. It is
only a cache: subscriptions are server-side, Steam reconciles against them
on its own schedule and would undo the edit, and it rewrites the file from
memory while running so an edit made with Steam open is simply lost. The
`manifest`/`latest_manifest` ids are content-addressed, so an invented one
invites Steam to conclude the local content is wrong and re-download or
remove it, and malformed KeyValues can have it discard and rebuild the file
for all items. It would also buy nothing: the game loads from the content
folder, and a faked entry does not create the subscription that would keep
an item updated. Synthetic `.acf` files remain the right thing for test
fixtures, which is where they are already used.

## Superseded

Supersedes D-021 §5's rule that the Asset status accordion requires an API
key. The rest of D-021 stands.
