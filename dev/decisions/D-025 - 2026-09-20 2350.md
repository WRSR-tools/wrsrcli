# D-025 - A help banner, per-command help, and Tab completion

- **Decided:** 2026-09-20 23:50

## Issue

`wrsrcli` with no arguments printed argparse's default help: a usage line,
"positional arguments", and a bare list of command names. D-017 already
established that someone typing the name alone is asking what the tool is,
and that a usage error is a poor answer — but so is a grammar summary.

Three things follow from fixing it: what the top-level screen should say,
how much each command should say for itself, and whether the shell can help
the user type any of it.

## Decision

### 1. The root screen is a banner, not a usage line

`wrsrcli` and `wrsrcli --help` now print an 80-column screen: a rule, the
name with `vX.Y.Z - YYYY-MM-DD` right-aligned, the website, a rule, the
description, the command list, the options, and a footer pointing at
`-h`. Subcommand help is left exactly as argparse renders it, because
there the usage line *is* the useful part — it shows the arguments.

The release date sits beside the version because the two answer different
questions: which build this is, and how old it is. It lives in
`__released__` next to `__version__`, so a release bumps both together and
neither can describe a different build from the other.

Colour follows D-016 and D-019: the rules, the name, the command names and
the section headings take the rust accent; everything else keeps the
terminal's own foreground, and all of it disappears under `NO_COLOR` or
when output is redirected.

### 2. Every command describes itself

Each subcommand gained a paragraph, and those with arguments worth
demonstrating gained an example block. The one-line help in the list says
what the command is for; `wrsrcli {command} -h` says what it does, what it
needs, and what it will not do.

The paragraphs name preconditions the user cannot otherwise guess — that
`scan` wants Steam running, that `output-table` does not, that `rollback`
takes the origin item's id and not the changed item's. Those are the
mistakes the old one-liners invited.

### 3. Tab completion is generated, not dynamic

`wrsrcli completion` prints a PowerShell `Register-ArgumentCompleter`
script; `--install` writes it into the user's profile after showing the
path and waiting for ENTER, and replaces any previous copy rather than
appending a second completer for the same command.

The command and option names are baked into the script when it is
generated, rather than the script shelling out to `wrsrcli` on each
keystroke. Tab has to feel instant, and spawning a process — a PyInstaller
one-file executable, which unpacks itself on every run — would not. The
cost is that the script is a snapshot, so upgrading means running the
command again; the script's own header says so.

PowerShell only. The tool is Windows-only (SPEC §1), and cmd.exe has no
equivalent mechanism.

**Known gap:** PowerShell does not invoke a native command's completer for
a bare `-` or `--`, so pressing Tab there offers nothing. One character
more — `-g`, `--p` — completes normally. This is the shell's behaviour, not
something the script can reach, and it is documented rather than worked
around.

### 4. `completion` is a command, not a flag

It takes an argument (`--install`), it has its own help, and a user looking
for it will look in the command list. A hidden flag would have been
smaller, but AGENTS.md's convention is one subcommand per verb, and this is
a verb.

## Superseded

Not superseded. D-017's rule — bare `wrsrcli` prints help and exits 0 —
still holds; this changes what that help looks like.
