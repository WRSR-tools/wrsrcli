# D-026 - Knowing the version is current, and `wrsrcli upgrade`

- **Decided:** 2026-09-21 00:30

## Issue

A released `.exe` had no way to tell its user it was old, and no way to
replace itself. Both were wanted. The questions are where "is this current"
is answered, and how a running Windows executable replaces itself without
leaving the user with nothing.

## Decision

### 1. One file per release, and the file is the message

The release workflow writes `versions/vX.Y.Z.txt` for each tag. The newest
says "This is the latest version."; every older one is rewritten to say it
is outdated and to run `wrsrcli upgrade`, keeping its own version and
release date.

`wrsrcli --version` fetches the one file named after its own build and
prints the line it finds. It does not compare versions, parse dates or
decide anything — the file already says what it needs to say.

That is the point of the design. The alternative, asking the releases API
what the newest version is, means every build carries comparison logic that
can only be fixed by shipping another build, and it spends a rate-limited
JSON request to answer a yes/no question. Here an old build makes one small
unauthenticated request for a static file, and **what a released build says
about itself stays editable after release** — a wording mistake, or a
release that has to be pulled, is fixed by changing a text file rather than
by hoping people upgrade.

The new file is written *before* the old ones are rewritten, so there is no
moment where every file says "outdated" and none names the version to get.

`upgrade` does use the releases API, because it needs the asset's download
URL and there is no way to know that in advance.

### 2. `--version` answers even when it cannot check

It prints the version number first and the note second. Someone offline,
behind a proxy, or running a build that was never released still gets the
answer to the question they asked; the check degrades to one line saying it
could not be made. The timeout is 2.5 seconds, because a version number
should not wait on a socket.

The note is printed in the accent only when it says "outdated". A green
"you are current" is noise; the one that matters should catch the eye.

### 3. Replacing a running executable

Windows will not delete or overwrite a running `.exe`, but it will rename
one. So `upgrade` downloads beside the current executable, renames the live
file to `.old`, and renames the new one into its place. The leftover is
deleted by the next run, which no longer holds it open.

Every failure leaves something that works. A failed download never reaches
the rename. If the first rename fails, nothing has moved. If the second
fails, the original is renamed back before the error is raised, so the user
is never left without a `wrsrcli`.

The downloaded file is checked for `MZ` before any of that happens. A
captive portal, a 404 page or a truncated transfer would otherwise be
renamed into place as the tool, and the next thing the user runs would be
whatever HTML they were served.

### 4. `upgrade` refuses when it is not the thing that was installed

Running from source or from pip, there is no executable to replace, so it
says to use `pip install -U wrsrcli` rather than doing something surprising
to a site-packages directory.
